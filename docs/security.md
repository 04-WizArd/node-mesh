# Security

## Threat model

| Actor | Can | Must not be able to |
|---|---|---|
| Anonymous internet client | reach the coordinator's public port | read, list or write any file; reach a storage node; make the coordinator spool data before authenticating |
| Authenticated user | manage their own files | see, download or delete other users' files; run script in other users' sessions |
| Host on the internal network (not holding a key) | send packets to nodes | store, read, list or delete objects; replay captured requests |
| Compromised storage node | serve wrong bytes, refuse service | make the coordinator serve corrupt data; impersonate the coordinator to other nodes (keys are per node) |

## Controls

**Users and sessions.**
- Django session authentication with Django's password validators.
- Login redirects; no tokens are returned.
- Logout is POST-only.
- Cookies are `HttpOnly` and `SameSite=Lax`, and `Secure` when `DJANGO_HTTPS=true`.
- The CSRF cookie is `HttpOnly`: the token is delivered in a `<meta>` tag.

**Authorisation.** Every file query is filtered by `owner=request.user`, and
foreign files return `404` (no enumeration). Storage nodes are never exposed to
clients; every byte goes through the coordinator.

**XSS.**
- Filenames are display strings only.
- The UI builds the DOM with `textContent`: no `innerHTML`, no inline handlers,
  no inline scripts.
- A strict CSP is sent: `script-src 'self'`, `object-src 'none'`,
  `frame-ancestors 'none'`.
- Downloads are always `application/octet-stream` + `attachment`, with
  `nosniff`, so uploaded HTML or SVG never renders in the app's origin.
- Regression tests: `test_no_html_sinks_in_frontend_code`, `test_no_inline_scripts_in_templates`.

**Input handling.**
- Upload size is checked from `Content-Length` *and* from the bytes actually received.
- Chunked uploads and multipart bodies are refused.
- A custom upload handler drops multipart file parts that the CSRF middleware
  would otherwise parse before authentication.
- Filenames are percent-decoded, stripped of path components and control
  characters, NFC-normalised and length-bounded.

**Storage paths.** Node keys are coordinator-generated UUIDs validated by the
URL converter. The on-disk path is derived from `uuid.hex` only, so traversal
is impossible by construction (tested with `../`, encoded `%2e%2e%2f` and
non-UUIDs).

**Internal authentication.**
- Per-node HMAC keys with key ids and rotation.
- Timestamp window, single-use nonces, constant-time comparison.
- The body is verified against the signed digest (see [api.md](api.md#request-signing-protocol-v1)).
- Nodes publish no ports in Compose, and the internal network has no external route.
- Network isolation is defence in depth; it is **not** relied on for authentication.

**Transport.** HMAC provides integrity and authenticity, not confidentiality.
- Within one Docker host, node traffic stays on a private bridge network.
- When nodes run on **other machines**, put the traffic in an encrypted channel:
  WireGuard or an SSH tunnel between hosts, or TLS in front of each node with
  `https://` base URLs. `NODEMESH_NODE_CA_BUNDLE` pins a private CA.
- Browser traffic should be terminated by a TLS reverse proxy. Then set
  `DJANGO_HTTPS=true`, `DJANGO_TRUST_X_FORWARDED_PROTO=true` and
  `DJANGO_HSTS_SECONDS`.

**Configuration.**
- No secrets are in the repository. Real values live in `.env` / `.env.cluster`,
  which are git-ignored, created with mode 0600 and generated by `scripts/init_env.py`.
- `DEBUG` defaults to `false`.
- Error responses are generic (`internal_error`); details only go to logs.
- `Credential.__repr__` redacts secrets, and logs never include keys or passwords.
- Containers run as non-root with `no-new-privileges` and all capabilities
  dropped; storage nodes also run with a read-only root filesystem.

**Supply chain.** The dependency list was rewritten by hand and every version
is pinned.

The legacy `requirements.txt` was UTF-16 encoded and pinned
`rest-framework-simplejwt==0.0.2`, a typosquatting package. It is removed,
together with DRF, simplejwt and django-cors-headers, which are no longer needed.

## Previously exposed secrets

The original academic code base contained hardcoded secrets: four Django
`SECRET_KEY`s and the credentials of a local PostgreSQL database. They were
committed to an earlier, private Git history. The repository history was then
restarted from this rebuilt code base: the first commit of the current history
contains none of the legacy files or values.

- **These values are compromised.** None of them is used by the rebuilt
  project; every environment generates its own keys with `scripts/init_env.py`.
  The old database password must be changed wherever it may still be valid.
- **The redaction is not retroactive.** Replacing a branch's history does not
  recall copies that already exist: older clones, forks, or cached views
  of the previous commits. Rotation is what actually neutralises the secrets.
- **Guarding against recurrence.** `.gitignore` excludes `.env*` (except the
  examples), key files and database dumps. CI runs on code that reads every
  secret from the environment.

## Known security limitations

- There is no rate limiting or lockout on login. Add it at the reverse proxy
  (or with a library such as `django-axes`) before exposing the service publicly.
- Data is not encrypted at rest on nodes. Use disk encryption on the hosts if needed.
- There is no per-user storage quota.
- The coordinator is trusted completely: anyone controlling it can read all data.
